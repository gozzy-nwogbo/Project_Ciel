# Second Brain — Project Vision

## What This Is

A personal AI second brain system built entirely within Claude Code. The goal is to synthesize the best architectures, strategies, and principles from two primary sources — **Nate B Jones's Open Brain** and **Cole Medin's Obsidian + Skills system** — into a single cohesive build that is owned, controlled, and maintained by me.

This is not a SaaS product. It is personal infrastructure.

---

## The Two Architectural Influences

### Nate B Jones — Open Brain
A database-backed, agent-readable knowledge system built on Supabase + pgvector, exposed via an MCP server so that any AI tool (Claude, ChatGPT, Cursor, future agents) can read and write to a single source of truth. The core insight: existing second brain tools (Notion, Apple Notes, Obsidian without the right layer) were built for humans browsing, not for agents querying. Open Brain solves the agent-readable problem at the infrastructure level.

Key components:
- Postgres (via Supabase) as the boring, stable source of truth
- pgvector for vector embeddings — every thought becomes semantically searchable by meaning, not just keywords
- Supabase Edge Functions for sub-10-second capture → embed → store pipeline
- MCP server with three tools: semantic_search, list_recent, stats
- Lightweight web UIs (generated by AI, deployed free on Vercel) as the "human door" to the same tables the agent writes to
- No sync layer, no middleware — the table is the single source of truth for both humans and agents

### Cole Medin — Obsidian + Claude Code + Skills
A file-based, local-first architecture using Obsidian as the knowledge canvas and Claude Code as the primary agent. The memory layer is inspired by OpenClaw (soul.md, user.md, memory.md) but built custom — so you control every permission and capability. Skills are modular instruction sets in `.claude/skills/` that give Claude Code specific capabilities (content generation, research pipelines, integrations) without bloating the context window.

Key components:
- Obsidian vault as the local markdown knowledge base
- CLAUDE.md as the instruction layer / navigation guide
- Session hooks (start, end, pre-compact) for automatic memory loading and promotion
- Daily log files + reflection cron job for the memory promotion pipeline
- Heartbeat system (via Claude Agent SDK) for proactive, autonomous daily actions
- Skills system with progressive disclosure — description tokens only until the skill is needed

## Build Approach

Extracted from Cole Medin's methodology:
- Build in phases — never try to build everything at once
- Use a PRD document as the planning artifact before writing any code
- Reference OpenClaw and other open-source projects as inspiration, not as something to run directly
- Start with the memory foundation (soul.md, user.md, memory.md, session hooks) — this is the core
- Add capabilities incrementally: integrations → skills → heartbeat → visual layer
- Zero trust mindset on permissions — start read-only, add write access deliberately
- The system should be able to reference itself and extend itself over time

## Forward-Looking Vision (Nate B Jones)

These are the ideal versions and highest-value possibilities described explicitly in the transcripts — not interpretations, not additions.

### The Chief of Staff Operation
The highest-value version of this system goes far beyond a daily digest. The second brain should power the entire workflow as one coherent system: meeting prep, email drafts, project planning, and relationship management all drawing from the same underlying memory. This is the version where the initial investment pays dramatically more dividends.

### The Compounding Flywheel — Models Getting Smarter Means Your System Gets Smarter
Every time a better model ships, every extension you have already built automatically becomes more capable. The agent reading your data today will, with next year's model, be automatically better at spotting conflicts, anticipating needs, and doing things you can't even imagine prompting for now. The data and structure you build today is the engine; improved models are free fuel that arrives over time.

### Cross-Table Reasoning as the Real Power
The power of the system is not in any single table — it is in the connections between tables that humans would never cross-reference themselves. Example: the system notices the dishwasher hasn't been serviced in six months, connects that to the meal planning table, and suggests stocking easy-to-clean dishes in the fridge because the maintenance person is going to need to come in. Multi-domain reasoning that a human sitting alone would never proactively generate.

### Time Bridging — The Agent's Core Advantage Over Human Memory
Agentic memory does not decay. Any problem where the value comes from linking events spread across months and years belongs to the agent: last dental checkup, last tire change, last dryer vent cleaning, annual LLC state filing, quarterly competitive analysis. Human memory is not designed for these. The agent is.

### The Warm Introduction Engine — Job Hunt Best Case
You paste a job posting into Claude and instead of it just reading the posting, it scans your contacts table, conference notes, and relationship data and surfaces: "You met someone from their data team at the conference in October. You noted a good conversation about distributed systems and they said they were hiring." That turns a cold application into a warm introduction. Additionally: a warm intro that was offered nine days ago and you forgot to follow up on gets caught overnight by an autonomous agent and flagged Monday morning — "the warm intro window is roughly two weeks."

### Interview Pattern Analysis Dashboard
After multiple interviews, a proactive web app visually surfaces patterns: four strongest interviews summarized with key strengths, insights about company size preferences, resume version tracking (version 1.3 is outperforming version 1.1). The whole pipeline visible at once over coffee, generated from the database.

### Relationship Health Dashboard — Proactive Network Expansion
The ideal version cross-references LinkedIn profile, email history, and Open Brain database to proactively suggest people to add to the network — people one degree away on LinkedIn, or people you've emailed someone at the same company as. Uses web search and personal data together. You didn't ask; it surfaced the opportunity.

### Open Brain as Infrastructure — API + SDK
The highest-ceiling version: build an API endpoint that lets other applications query the second brain, and work toward a reusable SDK that other developers can use to connect any application to personal knowledge infrastructure. The second brain is no longer a personal productivity tool — it is infrastructure that enables everything else you build.

### Skills + Evidence Layer
Generated content comes with built-in receipts showing what sources informed each output across the entire system. Not just a confidence score — full provenance embedded in every piece of output the system produces.

### The Four Criteria for Agent-Susceptible Problems
A framework for identifying which problems are worth building into Open Brain:
1. Time bridging — value comes from linking events spread across months and years
2. Cross-category reasoning — the insight only appears when multiple tables talk to each other
3. Agent surfaces, human decides, agent executes — agent handles memory and pattern recognition; human handles judgment and decisions
4. Scattered information over time — any problem involving scattered information, events spread out over time, and multiple categories needing cross-referencing

### Future-Proofing: Every Agent That Ships Can Plug In
When ChatGPT, Grok, or any other platform launches an autonomous agent product, it can be plugged directly into the MCP server immediately because MCP will be the universal protocol — "the HTTP of the AI age" and "the USB-C of AI." You build once, then receive every model upgrade and every new agent product as a free improvement.

### The "Open Brain as New Personal Computer" Framing
Just as people needed a personal computer to be digital citizens in the 1990s and 2000s, you need your own memory architecture to be a responsible AI citizen now. Building Open Brain is not a productivity hack — it is the fundamental infrastructure requirement of the current era.

### The Clarity Side Effect
The clarity required to organize information for an agent turns out to be clarity that makes you a better thinker and communicator. When you build a truly foundational memory architecture for AI agents, you are also doing better context engineering for your own human thinking.

### The Compounding Moat
Context is the actual moat, not the tools. If a competitor starts building their Open Brain six months after you, they are not just six months behind on setup — they are six months behind on accumulated intelligence that makes the system perform. The data logged, decisions captured, corrections saved, and patterns built up over that period cannot be recreated quickly.

## Self-Evolving Knowledge Base System (Cole Medin + Karpathy)

This is a distinct subsystem within the second brain — a knowledge base architecture that evolves automatically from session conversations. Inspired by Andrej Karpathy's LLM knowledge base tweet, Cole Medin adapted it for *internal* data (codebase/session conversations) rather than *external* data (internet articles). Both use cases apply here.

### The Compiler Analogy (Core Mental Model)
Knowledge management works like a compiler pipeline:

| Stage | Code Analogy | KB Equivalent |
|---|---|---|
| Source code | Raw code files | Raw folder — unprocessed inputs (articles, transcripts, session logs) |
| Compiler | Build process | LLM processing step — creates summaries, links documents, structures knowledge |
| Executable | Runnable binary | Wiki — compiled, cross-referenced, queryable knowledge |
| Test suite | Linting / tests | Health checks — gaps, stale data, broken links, raw-to-wiki discrepancies |
| Runtime | Running the app | Agent querying the wiki via index navigation |

### Vault Folder Structure for the KB
- `/raw/` — unprocessed source inputs (external: articles, papers, web clips; internal: raw session logs)
- `/knowledge/` or `/wiki/` — compiled knowledge that the agent actually queries
  - `/concepts/` — extracted ideas and insights from raw inputs
  - `/connections/` — how different concepts relate to each other
  - `index.md` — LLM auto-maintained navigation file listing all folders and resources; agent always starts here
- `agents.md` — global rules file explaining the entire knowledge system to the agent; loaded at session start alongside index.md

### The Index File (Replaces Fancy RAG)
Karpathy's key insight: "I thought I had to reach for fancy RAG, but the LLM has been pretty good about auto-maintaining index files." The index.md describes all available folders and resources. The agent starts from the index, navigates to the relevant section, and retrieves. No vector database needed for this layer — the agent traverses the graph via the file structure and backlinks.

### External Data Ingestion
- **Obsidian Web Clipper** — browser extension that clips any webpage directly into the `/raw/` folder as markdown
- Any article, paper, or transcript dropped into `/raw/` as unprocessed markdown becomes source material

### Internal Data Flow (Session → Wiki)
1. Session runs in Claude Code
2. Pre-compact or session-end hook fires → Claude Agent SDK summarizes the conversation transcript → summary saved to daily log in `/raw/`
3. **Flush process** (runs once daily via cron) → LLM extracts concepts and connections from all daily logs → populates `/wiki/concepts/` and `/wiki/connections/`
4. Index.md is updated to reflect new wiki content
5. Next session starts with `agents.md` + `index.md` already loaded → agent navigates to relevant wiki articles to answer questions

### Health Checks / Linting
Periodic process that scans the knowledge base for:
- Gaps — topics that need more research
- Stale data — outdated entries
- Raw-to-wiki discrepancies — items in `/raw/` not yet promoted to wiki
- Broken links — a document links to another that doesn't exist

### The Compounding Loop
Ask a question → agent searches wiki → answer is filed back into the knowledge base → wiki grows → future questions get better answers automatically. The more sessions run, the smarter the agent becomes on that codebase or knowledge domain — without any manual maintenance.

### Self-Awareness and Self-Improvement
Claude Code has access to `agents.md` which explains the entire memory system. This means Claude Code can explain how the system works, walk through customizations, and improve the flush/compile prompts on request. The system is self-contained and can improve itself.

### Setup
A single PRD prompt (from Karpathy's follow-up tweet, adapted by Cole) can oneshot the entire setup for any codebase. No additional integrations or installs required — only Claude Code hooks.

## Token Management & Agent Hygiene Principles (Nate B Jones)

Token efficiency is a builder skill, not just a cost concern. As frontier models get more expensive, wasteful habits scale. These principles apply to every session and every agent call in this system.

### The Core Mental Model
There are two modes that must never be mixed:
- **Gather information mode** — exploratory, multi-turn, multiple tools and models
- **Get work done mode** — focused, single-purpose; the objective is to be so clear that the AI does nothing except execute and return

Mixing these two modes is the primary driver of token sprawl.

### Document Ingestion
- Always convert documents to markdown before ingesting — raw PDFs can be 20x more tokens than the equivalent markdown (100k tokens vs 5k for the same 4,500-word document)
- Screenshots are extremely token-inefficient — copy and paste text instead
- Markdown conversion should happen before anything enters the context window or knowledge store
- Once inflated tokens are in the conversation history, they compound on every subsequent turn

### Conversation Management
- Start a fresh conversation every 10–15 turns — models drift in long conversations; they were never designed for that
- Every turn you take, the model reads the *entire* conversation history, not just your message
- Separate thinking conversations (exploratory, multi-model) from execution conversations (focused, single task)
- For evolving exchanges, state the goal at the top, reach the conclusion, then summarize and start fresh

### Plugin and Connector Hygiene
- Every plugin and connector loaded is a silent token tax on every single conversation
- Someone loading 50+ plugins/connectors can burn 50,000+ tokens before typing a single word
- Audit plugins regularly — remove anything you're not actively using
- Only load the tools you genuinely need for the current task; skills + progressive disclosure handles the rest

### Model Selection Strategy
- **Opus / most expensive model** — use only for complex reasoning tasks that genuinely need it
- **Sonnet** — use for execution (coding, structured output, most work)
- **Haiku** — use for polish, formatting, simple tasks
- Do not bring the Ferrari to the grocery store; use the right model for the job

### Prompt Caching (API / Agent Builders)
- Cache stable context — system prompts, tool definitions, persona instructions, reference documents
- Cache hits cost 90% less than standard calls (e.g., $0.50/M vs $5/M for Opus)
- Anything that doesn't change between calls should be cached; not doing this is pouring money away
- This is not advanced in 2026 — it should be default behavior

### Context Window Auditing
- Use `/context` in Claude Code to see exactly what's loading before you type
- As models get smarter, you can lean out the context window — trust the model to retrieve rather than frontloading everything
- Prune system prompts regularly — lines that made sense two model generations ago may no longer be needed

### Web Search Token Efficiency
- Perplexity via MCP burns 10–50k fewer tokens per search than native Claude web search
- 5x faster, produces structured citations
- For any research-heavy session, a dedicated search MCP (Perplexity or equivalent) is a meaningful optimization

### Token Audit — The "Stupid Button" Checklist
Six questions to assess token hygiene before any session:
1. Am I feeding raw PDFs or images when all I need is text?
2. When did I last start a fresh conversation?
3. Am I using the most expensive model for everything regardless of task?
4. Do I know what's loading in context before I type? (run `/context`)
5. Am I caching stable context for repeated agent calls?
6. How am I handling web search — is it as token-efficient as possible?

### For Agent Calls Specifically
- **Index your references** — never dump a full document set into the window; scope retrieval to what's needed
- **Prepare context for consumption** — pre-process, pre-summarize, pre-chunk before it hits the agent's context; a reference document should arrive ready to use, not ready to be processed
- **Cache stable context** — system prompts, tool definitions, reference docs; always
- **Scope each agent's context to minimum needed** — a planning agent doesn't need the full codebase; an editing agent doesn't need the project roadmap
- **Measure what you burn** — instrument agent calls, track input tokens, output tokens, model mix, cost ratio; you cannot improve what you don't measure

### Token-Efficient Open Brain Guardrails (to build into the system)
- Automatic markdown conversion for any document hitting the knowledge store
- Index-first retrieval — agent always starts at the index, not a raw document dump
- Context scoping — minimum viable context for each query type; not everything, just what's relevant

### TODOs — Token Management
- Build token audit skill that measures per-session token overhead and flags system prompt load, plugin/skill loading
- Build markdown auto-conversion pipeline for all document ingestion into the knowledge store
- Implement index-first retrieval as default agent behavior (agent reads index, then navigates)
- Set up Perplexity MCP for token-efficient web search
- Add prompt caching to all stable context (system prompts, tool definitions, core reference docs)
- Add `/context` usage to session start checklist — know what's loading before work begins
- Instrument agent calls: track input tokens, output tokens, model used, cost per call
- Prune CLAUDE.md and global rules on a regular schedule as models improve

## Agent Production Principles (Nate B Jones)

These are principles for deploying agents that actually work over the long term — not just on day one. Extracted from lessons about real-world OpenClaw/agent deployments that failed after initial success.

### Clarity of Intent First
Agents instantiate your intent — nothing more. If your intent is vague or generic, you get generic average output. Before building anything agentically, you must have clarity about what the system should do, why it's different from a generic solution, and what the specific workflows and edge cases are. Vague intent produces output that "works for everybody out of the box and therefore for nobody."

### Five Commandments for Agent Deployments

**1. Audit before you automate**
Map the actual process — not the idealized one. Include all edge cases, tribal knowledge, undocumented exception handling, and the things that live only in people's heads. This is the first thing you do, before a single agent call.

**2. Fix the data before you give an agent access to it**
Establish a source of truth. Define your schemas. Build your validation. Decide which system wins when two sources of truth disagree. Clean data is boring work and it is non-negotiable. The entire premise of Open Brain is having a clean data layer. An agent given dirty data becomes a dirty data engineer unless explicitly constrained.

**3. Don't mistake a skill for a process**
Business workflows should be hardwired and deterministic. The agent should operate *across* the rails of a well-defined process, handling the text composition and tool calls it's good at. Don't stick an entire business workflow into a skill file and hope the agent follows it reliably every time — it won't. Take the rails out and you'll have accidents.

**4. Build observability from day one**
Have an independent, preferably automated perspective that tells you whether the agent completed the task correctly. Do not rely on agent self-reporting. If you send something to a void and an answer comes back that you like, you do not have an agent — you have a problem masquerading as a helpful answer. Observability is not an afterthought.

**5. Scope authority deliberately**
Decide explicitly what the agent can and cannot do. Document it. Guardrail it. Do not give the agent free access to everything because it seems convenient on day one. This is one of the core sources of failure in agent deployments. Dangerous permission skipping may accelerate day one; it makes day 30 a disaster.

### Legibility of Surfaces
A key quality criterion for any agent system: can you see what the agent wrote? Is the data surface visible? If you can't trace what the agent stored, where it stored it, and why — you don't have an agent. You have a black box. Every system built here should have a visible, legible data surface.

### LLM as Evaluative, Not Just Generative
We put 10% of the thought into making agents evaluative and 90% into making them generative. This ratio needs to change. Agents that review PRs, evaluate output quality, flag anomalies, and auto-detect problems are just as important as agents that generate. Plan for evaluation as much as generation in the system design.

### The High-Speed Rail Analogy
The agent layer should be a dedicated track with no human traffic on it. Humans cluster around the handoff points — where data goes in and where data comes out. The work in between should be agentic end-to-end: structured, laid out, evaluated, and reliable. Mixing agents and humans mid-workflow causes accidents. Design the full agentic pipeline as its own lane.

### The Mini-Me Fallacy
Don't configure your agent as a mini version of yourself. Agents configured as mini-mes inherit all of your biases and blind spots, just faster. Configure your agent for the specific job it needs to do — define its workflows, its permissions, its evaluation criteria — and position yourself as the manager who brings judgment and overall direction, not as the person the agent is trying to imitate.

### TODOs — Agent Production Principles
- Document explicit security boundaries before any integration is built (what can never be done)
- Build observability / audit logging for every agent action from day one — independent of agent self-reporting
- Define and hardwire trigger conditions for any recurring process (don't leave process logic in skill files alone)
- Build a writer-critic pattern for any generative output that matters — one agent generates, another evaluates
- Define data schemas and validation rules before any agent writes to a table
- Document the actual process (with edge cases) before automating any workflow

## The Agent Infrastructure Stack (Nate B Jones)

A framework for understanding what agents actually need at the infrastructure level — and which layers are stable vs transitional. Builders need stack literacy: knowing which layer is their competitive advantage, which are shims they're betting on, and which will be replaced.

### The Six Layers

**Layer 1: Compute and Sandboxing**
Agents need somewhere safe to run code — isolated, sandboxed, auditable execution. The key architectural bet: *ephemeral* (spin up, run, spin down) vs *persistent* (agent state survives across sessions). This is not a style preference; it's a fundamental bet on how long agent sessions will run and whether state matters. Most mature layer in the stack.

**Layer 2: Identity and Communication**
Agents need to exist as entities on the internet, send/receive messages, authenticate with services, and hold verifiable identity. Email as identity is a pragmatic bet (not an architectural bet) — email is universal today but was designed for humans, not agents. Native agent-to-agent communication protocols are in development. Building on email as identity creates migration costs when native protocols arrive.

**Layer 3: Memory and Statefulness**
Agents need memory across sessions, tasks, and days — not just within a conversation. The right architecture is a hybrid data store: network graph + vector database + key-value store. Memory should be treated as active curation — deliberately storing important things, deliberately forgetting outdated or conflicting details, recalling only what's relevant. The risk: frontier labs are building memory into their models; standalone memory layers may get absorbed.

**Layer 4: Tools and Integration**
Agents need to interact with external tools — Slack, GitHub, Salesforce, Google Workspace, etc. The N×M integration problem: every agent builder independently managing credentials, auth flows, rate limits, error handling, and API schema changes for every tool. Managed integration layers exist to solve this. Long-term risk: if MCP becomes the universal standard, the value of managed integration diminishes.

**Layer 5: Provisioning and Billing**
Agents need to acquire services and pay for them. This is the trust layer for agent-to-service transactions. Dynamic budget allocation (agent A can spend X without human approval, agent B requires approval) and FinOps visibility across agent workflows are just emerging.

**Layer 6: Orchestration and Coordination**
The biggest gap and the biggest opportunity. What's missing and needs to exist:
- Scheduling and lifecycle layer — agent creation, assignment, health checking, scaling, termination as a managed service
- Merge and coordination infrastructure for parallel agent work — merge queues, conflict detection, resolution protocols
- Supervision hierarchies — meta-agents that monitor, evaluate, and course-correct other agents (as infrastructure you configure, not framework code you write)
- Financial observability — cost per agent, cost per successful task, FinOps for agents
- Standard failure and recovery patterns — when an agent's tool call fails, what happens should be standardized, not hand-rolled per team

### Three Builder Lessons for 2026

**1. Reliability compounds in the wrong direction**
When your agent depends on five primitives each at 99% uptime, your end-to-end system is 95% reliable. At 97% each, it's 86%. Every primitive you compose stacks its liability onto the system. Design to minimize the number of moving parts.

**2. Transitional lock-in is a real risk**
Every shim you adopt (email as identity, a managed integration layer, a specific memory SaaS) is a bet that it either becomes the standard or is cheap to swap out. Be explicit about which bets you're making and why.

**3. Agent sprawl is coming**
Not everything needs to be an agent. The same mistake that produced microservices sprawl is happening with agents. Build the minimum agent surface needed; resist the temptation to agentify everything. Design for composability and supervision from the start.

### New Builder Skills
- **Context engineering** — what you feed the agent determines its output; this is the primary leverage
- **Eval-driven development** — agents must be able to autonomously evaluate against a result; human review is a bottleneck
- **Stack literacy** — knowing which of the six layers is your competitive advantage and which are shims you're betting on

### TODOs — Infrastructure Awareness
- Decide on ephemeral vs persistent agent architecture before building the heartbeat system
- Plan observability infrastructure (cost per call, outcome quality, audit trail) before scaling any agent workflow
- Avoid building on shims where an agent-native alternative exists or is clearly coming
- Design the orchestration layer (even if simple) before running multiple agents in parallel
- Build supervision into the system from day one — a meta-agent or review process for outputs that matter

## The 12 Agent Primitives from the Claude Code Leak (Nate B Jones)

Anthropic accidentally leaked Claude Code's source map — a $2.5B run rate product. Nate analyzed the codebase and extracted 12 primitives organized into three tiers: day-one basics, operational maturity, and advanced. These are the non-glamorous plumbing decisions that separate a notebook demo from a production-grade agentic system. **Building agents is 80% this plumbing and 20% AI.** The most common failure mode is not underengineering — it is overengineering too early (building multi-agent coordination before you have a working permission system; building a plugin marketplace before sessions can survive crashes).

Each primitive is described as: the universal pattern → Claude Code's production manifestation → what this means for your system.

---

### Tier 1 — Day One Non-Negotiables

**Primitive 1: Tool Registry with Metadata-First Design**
Pattern: Define your agent's capabilities as a data structure *before* writing any implementation code. The registry answers "what exists and what does it do" without executing anything.

Claude Code maintains two parallel registries: a command registry (207 entries for user-facing actions) and a tool registry (184 entries for model-facing capabilities). Every entry carries a name, a source hint, and a responsibility description. Implementations load on demand from the registry. The separation is structural — not inferred by the model.

Why it matters: Without a clean tool registry you can't filter tools by context, you can't introspect your system without triggering side effects, and every new tool requires changes to orchestration code. The registry is the foundation everything else builds on.

For this system: build a `list_tools()` function that returns metadata for all registered capabilities without invoking them. Support runtime filtering. Define every tool by name + short description. Write this before asking the model to pick or execute a tool.

---

**Primitive 2: Permission System with Trust Tiers**
Pattern: Not all tools carry the same risk. Categorize that risk and apply different approval tiers per category.

Claude Code segments capabilities into three trust tiers:
- **Built-in tools** — always available, highest trust
- **Plugin tools** — medium trust, can be disabled on command
- **Skills** — user-defined, lowest trust by default

Every tier has different loading behavior, different permission requirements, and different failure handling. The shell execution tool (bash) alone has an 18-module security architecture: pre-approved command patterns, destructive command warnings, git-specific safety checks, sandbox termination, and more.

Pre-classification checklist for any action: Is it read-only? Mutating? Potentially destructive? Is there a pre-approved pattern? Is there a destruction detection step? Is there domain-specific safety? Is there permission logging — every decision granted or denied with enough context to replay it?

For this system: before any integration is built, classify every capability into a trust tier. Never default to full access. Every tool that can modify, delete, or send must have explicit approval logic.

---

**Primitive 3: Session Persistence That Survives Crashes**
Pattern: A session is not just conversation history. It is a recoverable state that includes conversation, usage metrics, permission decisions, and configuration. If any of those are missing on resume, the session won't behave the same as the original.

Claude Code persists sessions as JSON files capturing: session ID, messages, token usage (in and out), and enough state to fully reconstruct the query engine. A resume function does: load → reconstruct transcript → restore counters → return a fully functional agentic engine from a crash.

Why it matters: agents crash. Connections drop. Users close tabs. Every interruption that becomes a restart is a degraded experience. Build session persistence that is not just conversation history but the whole state ball.

---

**Primitive 4: Workflow State (Distinct from Session State)**
Pattern: When you resume a conversation, it is not the same as resuming a workflow. These are different problems with different solutions. Almost every agentic framework conflates them.

- **Chat transcript** answers: what have we said?
- **Workflow state** answers: what step are we in, what side effects have already happened, is this operation safe to retry, and what should happen after restart?

Without workflow state, an agent that crashes mid-tool-execution will potentially duplicate a write, double-send a message, or rerun an expensive operation on resume. Model long-running work as explicit named states: `Planned`, `Awaiting Approval`, `Executing`, `Waiting on External`. Persist checkpoints constantly — like saving a game every two seconds.

For this system: any multi-step workflow (heartbeat process, email draft pipeline, weekly review) needs workflow state persisted independently of session state.

---

**Primitive 5: Token Budget Management**
Pattern: Define hard limits before execution begins. Never discover you've exceeded limits at runtime.

Claude Code's query engine defines: maximum turns per conversation, maximum token budget per conversation, and a compaction threshold. Every turn calculates projected token usage. If the projection exceeds the budget, execution stops with a structured stop reason *before* the API call is made. The stop is clean, not a crash.

For agents: build hard stops for input tokens, output tokens, and turn count. A runaway loop that spends money you didn't intend to spend is a non-negotiable failure mode to prevent. This is responsible building in 2026.

---

**Primitive 6: Structured Streaming Events**
Pattern: Streaming isn't just about showing text. Every streaming event is an opportunity to communicate system state. Plan for failure paths in the stream design.

Claude Code's query engine emits typed events: `message_start`, `command_match`, `tool_match`, and others — all strongly typed throughout the execution stream. If the agent crashes, a special typed event with the crash reason is the last message the stream sends. It functions as a black box flight recorder.

Design principle: don't just emit raw chain of thought. Send typed events that communicate real information. Always include a crash event type so failures produce structured, interpretable output rather than silence.

---

**Primitive 7: System Event Logging**
Pattern: The conversational transcript tells you what the agent *said*. System event logging tells you what the agent *did*. These are separate concerns with separate solutions.

Claude Code maintains a history log of system events separate from the conversation: what context was loaded, what registry initialization looked like, what routing decisions were made, what execution counts accumulated, what permission denials or approvals occurred. Every event has a category and structured details sufficient to fully reconstruct any agentic run.

For this system: every consequential agent action (write to Supabase, send Slack message, create Asana task, draft email) must produce a structured system event, not just a conversational reply. This is the infrastructure that enables trustworthy auditing.

---

### Tier 2 — Operational Maturity

**Primitive 8: Two-Level Verification**
Pattern: Verification happens at two levels. Most systems only implement Level 1.

- **Level 1** — the agent verifies its own work as an explicit step in the harness after completing a task. Claude Code provides for this as a standard step.
- **Level 2** — verification tests that cover changes to the harness itself. When you modify the agent's configuration, you need tests that confirm the guardrails still hold: Do destructive tools still require approval? When tokens run out, does it gracefully stop or hard crash? These tests should be named, logged, and run against any harness change.

The lesson: provide for the harness evolving. Every time you change CLAUDE.md, global rules, or integration permissions, verification tests should confirm the behavioral guarantees haven't broken.

---

**Primitive 9: Tool Pool Assembly**
Pattern: A general-purpose agent doesn't load all available tools on every run. It assembles a session-specific tool pool based on context.

Claude Code assembles a tool pool per session based on mode flags, permission context, and deny lists — not a static list. With 184 tools available, no run loads all of them.

Design principle: allow agents to dynamically assemble a short tool list from a wider tool subset per run, rather than hard-coding which tools are available for every execution. This keeps context lean and allows the agent to reason about which capabilities it needs before it starts work.

---

**Primitive 10: Transcript Compaction (Production-Grade)**
Pattern: Conversation history is a token-expensive resource. Automatic compaction is not optional for longer-running agents.

Claude Code compacts automatically after a configurable number of turns. It keeps recent entries and discards older ones. The transcript store tracks whether the compaction has been persisted to avoid data loss during the compaction window.

Beyond what WHISK covers: you must decide what you keep, what your compaction threshold is, how you verify that what you kept is correct, and how you ensure compaction never causes data loss. This becomes critical as agents run longer and longer sessions.

---

### Tier 3 — Advanced

**Primitive 11: Permission Audit Trail as First-Class Object**
Pattern: Permissions are not a boolean gate (yes/no). Permissions are a state object that is easy to query, easy to audit, and easy to replay.

Claude Code builds three separate permission handlers to serve different agent contexts:
- **Interactive handler** — human in the loop
- **Coordinator handler** — multi-agent orchestration; the orchestrator agent hands out permissions to sub-agents
- **Swarm worker handler** — autonomous execution managed by an orchestrator agent

Three different agent types exist in the same system and need structurally different permission architectures. Design for all three, even if you only start with the interactive handler.

---

**Primitive 12: Agent Type System**
Pattern: Don't spawn agents randomly. Constrain roles sharply and define observable types so you can manage your agent population and control the efficiency of their work.

Claude Code defines six built-in agent types, each with its own prompt, allowed tools, and behavioral constraints:
- **Explore** — cannot edit files
- **Plan** — doesn't execute code
- **Verify** — checks work against known criteria
- **Guide** — provides direction without acting
- **General Purpose** — full capability within permission scope
- **Status Line Setup** — lightweight status and configuration

The transferable lesson: when you split work across agents, constrain each role to a named observable type. This makes your agent population manageable, auditable, and efficient.

---

Nate released a skill that operationalizes these 12 primitives. It has two modes:

- **Design mode** — describe the agent you're building; the skill runs a structured design process, recommends a harness shape, identifies the minimum useful set of primitives, sequences implementation into phases, and defines verification criteria — all before writing a line of code. Biases toward lean, solo-maintainable architecture. Starts with single-agent design unless given strong reasons otherwise.
- **Evaluation mode** — point it at an existing codebase or CLAUDE.md; it evaluates every dimension against the 12 primitives and returns findings ordered by severity, a prioritized upgrade path, and specific tests that confirm fixes work.

The skill biases toward simplicity intentionally because premature complexity is where most agentic projects die.

**Primitive 7: System Event Logging (Separate from Conversation Transcript)**
The conversational transcript captures what was said. The system event log captures what was done. These are separate concerns.

Claude Code maintains a history log that records: what context was loaded, registry initialization, routing decisions, execution counts, permission approvals and denials. Every event has a category and structured details, so any agentic run can be fully reconstructed.

*Without system event logging:* when something goes wrong, you cannot provably trace what the agent did. You have no audit trail. You cannot replay decisions.

*Applied here:* every agent action — context load, tool call, permission decision, state transition — gets an event log entry with category + structured details. This log is separate from the conversation and is the source of truth for what happened.

---

#### Tier 2 — Operational Maturity

Build these once Tier 1 is stable.

**Primitive 8: Verification at Two Levels**
Most teams implement one level of verification. Claude Code implements two.

- **Level 1:** The agent verifies its own work after each run. An explicit verify step in the harness. Expected, important, necessary.
- **Level 2:** Verify that changes *to the harness* don't break guardrails. When you modify the harness, you change every subsequent agent run. You need tests that confirm the harness still works correctly after changes: do destructive tools still require approval? Does the model stop gracefully when tokens run out? These should be named, logged, and automated.

*Applied here:* build verification as a named step in the agent loop. Build a separate harness test suite that runs after any change to agent configuration, permission rules, or capability definitions.

---

**Primitive 9: Tool Pool Assembly**
With 184 tools available, Claude Code does not load all of them on every run. It assembles a session-specific tool pool based on mode flags, permission context, and deny lists. The agent reads a relevant subset and picks from that list for the given run.

*Applied here:* for any general-purpose agent, build dynamic tool pool assembly rather than hardcoding a fixed tool list. The agent should be able to read a wider capability registry and select the minimum tool set needed for the current task.

---

**Primitive 10: Transcript Compaction**
Conversation history is token-expensive. Claude Code automatically compacts it after a configurable number of turns, keeping recent entries and discarding older ones. The transcript store tracks whether it has been persisted to prevent data loss. The critical constraint: the original instruction that started the agent must be preserved across compaction.

*Applied here:* build automatic compaction with a configurable threshold. Define what to keep (recent context, the original instruction, key decisions) and what to discard (intermediate turns that no longer affect the current state). Always verify the original goal survives compaction.

---

**Primitive 11: Permission Audit Trail**
Permissions should not be a boolean gate. They should be a first-class state object that is easy to query.

Claude Code builds three separate permission handlers for three different execution contexts:
- **Interactive handler** — human in the loop
- **Coordinator handler** — multi-agent orchestration, where an orchestrator agent hands out permissions to sub-agents
- **Swarm worker handler** — autonomous execution managed by an orchestrator

*Applied here:* even before reaching multi-agent complexity, build permissions as queryable state objects — not boolean flags. Design the permission architecture to support all three handler types so the system can grow into them without rebuilding.

---

**Primitive 12: Agent Type System**
Do not spawn agents randomly. Constrain roles sharply.

Claude Code defines six built-in agent types, each with its own prompt, allowed tools, and behavioral constraints:
- **Explore** — cannot edit files
- **Plan** — does not execute code
- **Verify** — checks work, does not produce
- **Guide** — provides direction, does not act
- **General purpose** — full capability set
- **Status line setup** — narrow setup task

*Applied here:* define named agent types before building multi-agent workflows. Each type should have an explicit capability boundary. Managing your agent population by type is what allows you to reason about, debug, and control larger systems.
